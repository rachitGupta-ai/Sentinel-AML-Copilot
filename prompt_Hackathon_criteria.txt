# Role

Act as a principal enterprise architect, Snowflake AI engineer, product strategist,
security architect, data modeller, hackathon judge, and technical product manager.

Your responsibility is to deeply analyse the five official Snowflake CoCo CLI
Hackathon 2026 GCC Edition challenges and transform the selected challenge into
an implementation-ready, production-oriented project.

Do not immediately generate application code.

First understand the challenge, investigate the business problem, identify
ambiguities, compare possible approaches, select the strongest project direction,
and create a complete project specification.

The objective is not to build another generic chatbot or dashboard.

The proposed solution must:

1. Solve a credible enterprise problem.
2. Use Snowflake CoCo CLI meaningfully.
3. Combine AI reasoning with governed enterprise data.
4. Produce measurable business outcomes.
5. Demonstrate an end-to-end workflow.
6. Include security, governance, observability, explainability, and failure handling.
7. Be achievable as a working hackathon prototype.
8. Have enough differentiation and visual impact to impress judges.

---

# Official Evaluation Rubric

Evaluate every decision against these weights:

- Technical Execution: 40%
- Real-World Relevance: 30%
- Solution Completeness: 30%

Create a traceability matrix showing how the proposed solution satisfies every
part of the rubric.

Do not invent additional official judging criteria.

You may introduce internal engineering quality gates, but clearly label them as
recommended project standards rather than official hackathon criteria.

# Official Challenges

## Challenge 1: Risk, Fraud and Regulatory Intelligence Copilot

### Business context

Banking and NBFC teams manage:

- Real-time fraud
- Liquidity risk
- Credit risk
- AML requirements
- Basel-related reporting
- Local regulatory requirements
- Audit and evidence preparation

Many of these activities are still fragmented or manually executed.

### Required outcome

Build a copilot that:

- Surfaces risk and fraud signals
- Supports questions in natural language
- Produces audit-ready regulatory outputs
- Connects analytical results with source evidence
- Makes risk findings understandable and traceable

### Deep-analysis questions

Analyse:

1. Who are the primary users?
2. What decisions does each user need to make?
3. Which structured and unstructured data sources are required?
4. How would fraud, credit risk, liquidity risk, AML, and regulatory reporting
   interact without creating an excessively broad prototype?
5. Which use case should be the primary scenario?
6. What should be explicitly excluded from the MVP?
7. What is the difference between a risk signal and a confirmed risk event?
8. How will the system avoid presenting an AI-generated claim as a regulatory fact?
9. How will every insight be linked to data, policy, model version, and calculation?
10. How will false positives, model drift, stale data, and missing records be handled?
11. Which actions should be automated?
12. Which actions must require human approval?
13. What would make an output genuinely audit-ready?
14. Which measurable business and technical KPIs would demonstrate value?
15. How will the demo prove that the system is more than a chatbot?

### Candidate capabilities to evaluate

- Fraud event ingestion
- Transaction anomaly detection
- Customer/entity risk aggregation
- AML case summarisation
- Regulatory-policy retrieval
- Natural-language investigation
- Evidence-backed answers
- Case creation
- Human approval workflow
- Regulatory report generation
- Immutable audit trail
- Risk threshold configuration
- Explainability and citation panel
- Adversarial-query protection

## Challenge 5: Supply Chain Ontology and Governed Conversational Analytics

### Business context

Supply-chain data is fragmented across:

- ERP platforms
- Logistics systems
- Supplier systems
- Order-management systems
- Plant systems
- IoT sources

Definitions and calculations often differ across departments, causing the same
question to produce inconsistent answers.

### Required outcome

Build:

- An industry ontology
- A business entity and relationship model
- Governed semantic views
- A natural-language analytics layer
- Consistent and trustworthy answers based on shared definitions and metrics

Example relationship chain:

Supplier → Part → Plant → Shipment → Order → Customer

### Deep-analysis questions

Analyse:

1. Which business domain should the prototype focus on?
2. Which supply-chain entities are essential?
3. What relationships connect these entities?
4. Which business terms commonly produce conflicting interpretations?
5. How should metrics such as on-time delivery, fill rate, lead time, inventory
   exposure, supplier risk, and perfect order rate be defined?
6. How will metric definitions be versioned and governed?
7. How will synonyms and organisation-specific terminology map to canonical concepts?
8. How will users see the semantic interpretation of their question?
9. How will ambiguous questions be detected?
10. When should the system ask a clarifying question?
11. How will row-level and column-level security be respected?
12. How will users trace an answer from natural language to semantic definition,
    generated query, source records, and final calculation?
13. How will incorrect cross-domain joins be prevented?
14. How will schema evolution be handled?
15. How will the system prove that two departments now receive the same answer?
16. Which operational decisions can be initiated from an analytical finding?
17. What makes this solution more valuable than text-to-SQL?
18. How will semantic consistency and answer accuracy be measured?
19. How can the demonstration intentionally show and resolve an ambiguous question?

### Candidate capabilities to evaluate

- Supply-chain ontology
- Business glossary
- Entity relationship model
- Governed semantic views
- Metric-definition registry
- Synonym resolution
- Natural-language query planning
- Ambiguity detection
- Clarification workflow
- Query generation
- Query validation

# Phase 6: Agent and CoCo CLI Design

Do not use “agentic AI” as a marketing label.

Define the exact responsibilities of each agent or skill.

Prefer a small number of focused components over unnecessary multi-agent complexity.

For every agent or CoCo CLI skill specify:

- Name
- Purpose
- Input contract
- Output contract
- Permitted tools
- Prohibited actions
- Required evidence
- Decision boundaries
- Confidence threshold
- Retry strategy
- Timeout
- Fallback
- Human-approval requirement
- Audit events
- Test cases

Determine whether the project needs:

- One orchestrator with modular skills
- Multiple specialised agents
- Deterministic workflow with selective AI calls

Select the simplest architecture that satisfies the use case.

Create a state machine such as:

RECEIVED
→ VALIDATED
→ ENRICHED
→ ANALYSED
→ EVIDENCE_COLLECTED
→ RECOMMENDATION_READY
→ POLICY_CHECKED
→ AWAITING_APPROVAL
→ APPROVED / REJECTED
→ ACTION_STARTED
→ ACTION_COMPLETED / ACTION_FAILED
→ VERIFIED
→ CLOSED

Include compensating behaviour for partial failure.
